# Kiln V2

Kiln V2 is the first public generation of the project: a small, inspectable,
board-free compiler foundation for deterministic TinyML inference.

The project began as an ambitious experiment to build a “QEMU of TinyML”. V2
turns that idea into a usable core with a versioned intermediate representation,
a virtual target, an independent integer reference, and generated C that can be
audited before it reaches a device.

## What V2 means

V2 is a generation boundary, not a promise that every model or board is already
supported. The stable center is deliberately small:

- KIR v1 JSON graphs and graph-plus-weights bundles.
- A deterministic KIR VM with traces and resource metrics.
- A PyTorch `torch.fx` frontend for the documented operator subset.
- A standalone C99 backend with zero dynamic allocation in generated inference code.
- Static arena, ROM, MAC, and int32 accumulator safety reporting.
- An independent integer reference used for differential and edge-case testing.
- Host linking and experimental Cortex-M/QEMU target paths.

## Who V2 is for

- Embedded engineers who need inspectable generated C and explicit resource bounds.
- Students who want to learn compiler, quantization, and verification concepts
  without owning a development board.
- Researchers who want to serialize, inspect, modify, and replay a small integer
  graph without importing PyTorch at every stage.

## V2 guarantees

Within the documented KIR v1 subset, Kiln aims to provide reproducible evidence
for each claim:

- identical inputs produce identical KIR execution and generated C;
- the generated model uses no dynamic allocation;
- generated C agrees bit-for-bit with the independent integer reference on the
  tested and adversarial inputs;
- resource usage is reported before deployment;
- unsupported graphs and unproven safety conditions fail with diagnostics.

The int32 result is a conservative static interval-analysis certificate, not a
machine-checked theorem. The VM cycle count is a deterministic virtual-target
estimate, not silicon latency. Host and QEMU results are not physical-board
evidence. These distinctions are part of the V2 contract.

## What V2 does not claim yet

- It is not a universal PyTorch, ONNX, or TFLite importer.
- It does not provide a turnkey RP2040 or other physical-board workflow yet.
- It does not claim production security classification from the Hazard example.
- It does not replace a full training framework or a general-purpose runtime.

See the [support matrix](SUPPORT_MATRIX.md), [KIR compatibility policy](../KIR_COMPATIBILITY.md),
and [target validation contract](../TARGET_VALIDATION.md) before relying on a
feature or measurement.

## The path after V2

V3 expands the public surface: more model formats, broader operator coverage,
SDK integration, and beginner-friendly workflows. V4 focuses on long-lived
trust: verified hardware profiles, stronger formal or bounded checking, and an
ecosystem of external frontends and backends. Neither generation should weaken
the fail-closed and evidence-first principles established in V2.
